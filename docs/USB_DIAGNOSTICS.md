# USB診断版 0.47.1

WebUI停止とUSBポートの消失を調べるための統合診断版です。
原因が解消したと判断した版ではありません。全体の調査結果は
[INSTABILITY_REVIEW.md](INSTABILITY_REVIEW.md)に記載しています。

## 最初の確認

1. [書き込みページ](https://temesotejam.github.io/atoms3r-free-foot-amplitude-control/)
   の表示が **0.47.1 USB診断版** であることを確認して書き込みます。
2. 書き込み画面を閉じてポートを解放し、通常起動します。
   Download Modeのままではアプリの診断ログは出ません。
3. 同じページの「USBシリアルに接続」で対象ポートを選択します。
   起動直後の8秒間は接続用の待機で、その後に通常処理が始まります。
   USB未接続でも8秒後に進みます。従来の10秒の立位案内待ちはその後です。
4. まず測定を開始せず、起動から停止・再起動までのログを取ります。
   装置Wi-Fiの接続前と接続後、WebUIを開いた前後を分けて観察すると、
   HTTPアクセスが必要な故障かを区別できます。
5. 問題が発生したら、可能なら復帰後の数回分まで受信して「ログを保存」でTXTを保存します。
   接続をやり直してもログは消しません。「ログをクリア」だけが明示的な消去です。

ポートの再出現時は許可済みポートに自動再接続します。最初に選んだポートを優先し、
同一VID/PIDの候補に置き換わった場合は候補が一つだけのときに再接続します。
複数候補の場合は選び直しを求めて停止します。受信のみで、リセット信号、
カメラ操作、測定開始、再書き込みは送信しません。PC側の接続イベントには時刻が付きます。

## ログの読み方

`USBDBG`で始まる診断を約1秒ごとに繰り返します。起動時だけの一回限りの表示ではありません。

| 項目 | 意味 |
|---|---|
| `boot,version` | 実際に動作しているファームウェア版 |
| `boot,id` | 有効なRTC記録が引き継がれた起動回数。電源断で1に戻ることがある |
| `reset` / `reset_id` | 今回の起動に至ったESP-IDFのリセット理由 |
| `stage` | USB待機、M5、logger、IMU、camera、roller、runner、control、feet、export、web、readyの到達段階 |
| `failures` | 初期化関数の失敗ビット。段階の順にbit 0〜11。0でも実行中の健全性は保証しない |
| `observer=1` | Core 0の独立USB観測タスクを作成できた |
| `observer=0` | タスク作成に失敗しArduinoループで代替出力中。HTTP停止時の独立性はない |
| `previous_boot` | 今回リセットの前の起動で残された初期化段階と失敗ビット |
| `previous` | 前回起動中、最後にRTCへ保存できた各処理の状態 |
| `live` | 現在の各処理の状態 |
| `phase` | 観測時に実行していた処理、または待機状態 |
| `seen` / `beats` | 完了報告を一回以上出したか、その累積回数 |
| `age_ms` | そのタスクの最後の完了報告からの経過。`seen=0`は未観測 |
| `stack_bytes` | そのタスク自身が約1秒ごとに確認した最小残存スタック。ESP-IDFではバイト単位 |
| `heap_at_ms` | メモリを調べた時刻。数値の更新が止まっていないかも見る |
| `internal` / `min` / `largest` | 内部ヒープの空き、過去最小の空き、最大連続領域 |
| `dma` / `psram` | DMA対応ヒープ／PSRAMの空き。内部ヒープとDMAは重複するので足し算しない |
| `ap` / `clients` | Wi-Fiイベントで観測したAP状態と接続台数。HTTP成功を意味しない |
| `usb_dropped` | PCへ出せないまま2秒経過した古い診断出力を捨てた回数 |

`detail`はcontrolで状態ID、IMUで直前の取得処理時間µs、cameraでフレーム取得の試行連番、
rollerでI/O準備状態（1/0）、exportでCRC計算済みバイトです。cameraの連番は
画像成功数ではありません。HTTPは0です。exportの待機中は長時間`age_ms`が増えて正常です。
cameraは終了後も待機ループの完了報告を更新します。

| 観察結果 | 次に調べる箇所 |
|---|---|
| `reset=PANIC` | 直前の例外・バックトレース、スタック、ヒープ破損、アサーション |
| `TASK_WDT` / `INTERRUPT_WDT` | CPU時間の独占、長いクリティカル区間、ドライバ／ロック停止 |
| `BROWNOUT` | 本体の電圧降下と共通給電経路。バッテリー利用だけでは除外できない |
| `POWERON`が繰り返される | 電源断、ENリセット、RTCを保持しないリセットなど。電圧波形で確認が必要 |
| boot IDは同じでHTTPの`age_ms`だけ増える | `http_poll`、JSON、メモリ、送信、ソケット終了のどこで止まったか |
| control/IMUの`age_ms`が増える | 取得、制御処理、スナップショット用ロック、スケジューリング |
| カメラの`age_ms`が増える | 取得、画像処理、バッファ返却、カメラ停止処理 |
| 複数の`age_ms`が同時に増える | 共通ロック、割込みやCPUの占有、ドライバ／メモリ待ち |
| USBが消えて再出現しても同じboot ID・時刻が継続 | 本体再起動とは限らない。USB経路やPC側を調べる |

## 実装と限界

- Core 0・優先度2・スタック6144 bytesのタスクをM5初期化より前に作成します。
  各タスクはロック不要の32bit観測値を書くだけです。観測タスクは制御・カメラ・
  IMUのlive snapshot、I2C、ネットワーク、ヒープAPIを呼びません。
- メモリ取得はsetup/HTTP所有タスクで約1秒ごとです。メモリ取得自体が止まっても
  USB観測タスクが同じロックを取りに行く構造にはしていません。
- 初期化段階はsetupだけが、実行中の状態は観測タスクだけが別々のRTCジャーナルへ保存します。
  実行中の保存間隔は約250ms。2スロットとCRCにより書き込み途中のリセット時は
  直前の完全な記録を採用します。フラッシュへの定期書き込みはありません。
- RTC記録は完全な電源断や一部リセットでは残りません。POWERONでは過去記録を採用しません。
  `previous`は停止命令の直前のPC値ではなく、最後に保存できたサンプルです。
- 観測値は項目ごとの近似スナップショットです。同時刻に全項目が確定したものではありません。
  カウンタや時刻は32bitで、長期稼働時のwrapがあります。
- 出力は固定3072-byteバッファ、128-byteずつの送信、1msのHWCDC送信待ちです。
  PC未接続を待つループや`Serial.flush()`は追加しません。
- 観測にもCPU/RAMを使います。スタック走査とメモリ走査のコストもあるため、
  この版の実測時間を診断なしの版の性能と同一視しません。ESP32全体や観測タスクのコアが
  止まる故障、USB自体の故障、setupより前の故障ではログが出ないことがあります。
- 例外時のUSB出力はSDKに依存し、必ず取得できるとは限りません。
  起動後にリセット理由を繰り返すのは取り逃しを減らすためです。

制御式、400/200HzのIMU設定、固定3ms補償、300mA/100msの制限、30秒測定、
開始・終了LED同期、左右足角度、RWLOG/CSV、再開可能なログ取得は継続します。
WebUIは状態形式の検査、最後の有効状態の保持、失敗時の操作無効化、
例外後も次のpollを予約する処理を追加しています。

## 検証

`bash tools/test_runtime.sh`で既存の制御・IMU取得・立位・足角度・最大ログ・CRC検証に加え、
RTC記録の部分書き込み／ビット破損／番号wrap、USB切断後の再接続とログ保持、
読取ロックの解放、再接続無効化、不完全JSON／描画例外からの復帰を確認します。
GitHub ActionsでESP32-S3実機向けビルドを行い、公開後にビルドSHA、
BMI270パッチの由来、4つの書き込みバイナリのSHA-256を検査します。
実機での安定動作と故障原因の特定は、この検証とは別です。
