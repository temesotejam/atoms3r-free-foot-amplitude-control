# 0.47.24：IMU起動経路と割り込み配置の分離

## 根拠となった0.47.23の実機結果

8°・30秒・3 ms予測の5回はすべてFINISHED。60,708回の制御完了中、
2.5 ms超過は4回（すべてRun 2）、最大2,969 µs、平均516.100 µsだった。
0.47.22の5回は60,709回中0回、最大2,325 µs、平均483.678 µs。
異なる試行間の比較なので、差のすべてをWi-Fiだけに帰属させることはできない。

| 項目（5回中の最大） | 0.47.22 | 0.47.23 |
|---|---:|---:|
| 読取完了→制御側Received記録 | 581 µs | 1,730 µs |
| IMU起動通知間隔 | 1,053 µs | 1,895 µs |
| 通知→取得処理開始 | 48 µs | 805 µs |
| 読取完了→runner return | 2,325 µs | 2,969 µs |

最大超過サンプルはReceived=1,154、Derived=1,261、MEKF=2,721、
Ready=2,759、Done=2,969 µs。新しいパルス決定のDecision記録はない。
Received→Ready間の取得処理との重なり1,040 µsはI/O待ちも含む経過時間であり、
CPUが奪われた時間そのものではない。Derived→MEKFにも姿勢ガイドなどが含まれ、
MEKF演算単体の実行時間ではない。

以前の詳細保存は1秒ごとの最大値のみだったため、超過4回のうち3回の詳細しか
残っていない。残る1回は入力別集計で2,580 µsと分かるが、その時刻・段階は不明。

## 変更内容

### IMU通知をCore 1のハードウェアタイマーへ

取得を起こす1,000 µs周期の通知を、Core 0のESP_TIMER_TASKから
TIMG1/T0のCore 1割り込みへ変更した。APB 80 MHz / 80の1 µsカウント、
自動リロード、レベル1、IRAM対応で初期化する。TIMGのウォッチドッグは別機能。
このタイマーは本アプリ専用で、HTTP・START・CLEARでは停止／再初期化しない。

割り込み内は時刻・通知間隔・実行コアの保存とvTaskNotifyGiveFromISRのみ。
I2C、浮動小数点、文字列生成、USB出力、メモリ確保は行わない。
IDFの標準ISRが割り込み解除・再設定・必要なタスク切替を担当する。
途中の初期化失敗では、割り込みを停止・解放してから取得タスクを削除する。

取得タスクはCore 1・優先度6、制御はCore 1・優先度4を維持。
加速度200 Hz、ジャイロ400 Hz、読み出しレジスタと1 msポーリング周期、
32件キュー、順序保証、10 ms以上の滞留停止も維持した。
タイマー通知の遅延は2.5 ms計測開始前である。通知経路の改善だけで
読取後の超過が解決するとは断定せず、取得間隔と完了遅延の両方で評価する。

### カメラ初期化・解放とWi-FiイベントをCore 0へ

カメラの処理タスクだけでなく、esp_camera_initを呼ぶ初期化全体を
Core 0の一時タスクで行う。DMA・フレーム同期割り込みも登録側のCore 0になる。
初期化失敗時の解放も同じタスク内で行い、debugDeinitもCore 0へ配送する。
初期化の戻りを待ってからRoller485を起動するため、カメラの一時SCCB用I2C0と
Roller485のI2C0所有権は重ならない。既にCore 0から呼ばれた場合は直接実行する。
完了用セマフォと呼出情報は、処理が終わるまで呼出側が保持する。

ArduinoのARDUINO_EVENT_RUNNING_COREを0に指定した。Wi-Fi本体・TCP/IPの設定、
AP維持と運転中HTTP休止、停止後のHTTP再開は0.47.23のまま。

カメラ画像取得・足検出・校正・MEKF・制御則・電流モデル・3 ms予測は変更していない。
前後±90°のSTOPと横倒しを対象外にする条件も維持。
Core 0への割り込み移動がカメラ／Roller I/Oの遅延に与える影響は実機で確認する。

## 追加記録

RWLOGのバイナリ行・CRC・ファイル形式は変更せず、停止後に作るJSONメタデータを拡張。
新しい計測情報はUSB診断の有効化に依存しない。USB診断は引き続き初期値OFF。

`control_latency.fields`の既存15列はそのままに、以下の5列を末尾へ追加した。

| 列 | 意味 |
|---|---|
| queue_submit_age_us | 読取完了→成功したxQueueSend呼出の直前 |
| queue_receive_age_us | 読取完了→採用するxQueueReceiveの直後 |
| delivery_valid | 上記2時刻が取得済みなら1 |
| pulse_active_at_entry | runner入口のパルス有無 |
| accel_fresh_at_entry | runner入口の新しい加速度の有無 |

submit→receiveにはキューAPI内のコピー・後続の取得側処理・スケジューリングを含む。
Receivedは従来どおり配信監査後の記録。これにより読取後の梱包、キュー経路、
受取後の監査を分けて評価できる。32 bitのmicros折り返しにも対応する。

`control_latency.overrun_detail`は、2,500 µsを厳密に超えたサンプルを
発生順に最大64件保存。同一秒内の複数回も残す。totalは全超過数、storedは保存数、
overflowは詳細を保存できなかった件数で、total=stored+overflowを満たす。
従来のworst_samplesも維持。記録領域は固定長の内部RAMで、全Profileは10 KB未満。
詳細のコピーは既存のrunner-return時刻取得後に行う。
計測の起点・終点・2.5 ms基準は変更していない。

`v46n_imu_acquisition.poll_trigger`にタイマー割当コアと実際のISRコアを追加。
`execution_placement`にカメラ初期化・解放呼出のコアとWi-Fiイベントの観測コアを追加。
-1は未観測。これらはboot→exportの観測であり、カメラISR自体のトレースや
運転中のPC接続維持の証明ではない。

## 検証

- 実際のタイマー設定処理を使ったモック試験で、誤ったコア／周期の拒否、
  各初期化段階の失敗とIRQ解放順序、二重初期化拒否を確認。
- カメラの同期ハンドオフ、Core 0直接呼出、タスク／セマフォ確保失敗を確認。
- 実ImuManagerの273条件のホスト試験。ISRはI2Cを読まず、通知時刻の折り返しを扱う。
- 2,500 µs境界、同一秒内の連続超過、64件上限とあふれ、CLEAR相当のリセットを確認。
- 最大イベント数・768足フレーム・64超過詳細を同時に含むRWLOGで、
  CRC、途中中断からの再開、JSON、足CSV、破損拒否を確認。
- MEKF／制御数値の既存回帰、姿勢STOP、HTTP休止・復帰、USB初期値OFFの回帰を実行。
- ESP32ビルド時には、新しいタイマーISR・IDF ISR・時刻関数・ISR通知関数のIRAM配置を検査。

ホスト試験とビルドは実機の時間保証ではない。0.47.24の連続運転、期限超過数、
IMU取得間隔、足観測、Roller I/O、Wi-Fi維持、終了後のダウンロードは実機検証待ち。
