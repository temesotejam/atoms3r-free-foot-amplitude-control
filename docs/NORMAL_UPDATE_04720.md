# 0.47.20: 通常の姿勢更新の実行を軽くする

0.47.19 の5回すべてで30秒の統合測定が完了した。取得エラー、キュー落ち、
配信順序の欠落、足観測の校正範囲越えはなかった。処理超過は大きく減ったが、
2.5 ms 以内という目標にはまだ達していない。0.47.20 は残る通常更新の負荷を
減らすための次版であり、実機での時間短縮量は未確認。

## 比較の根拠

目標8°・30秒・補償3 ms の各5回を合算。平均は各カウンターの件数で加重した。

| 指標 | 0.47.18 | 0.47.19 |
|---|---:|---:|
| 取得完了→runner終了の2.5 ms超過 | 533 / 60,713 | 124 / 60,710 |
| 超過率 | 0.878% | 0.204% |
| 同区間の平均 | 970.7 µs | 870.4 µs |
| 同区間の最大 | 5,582 µs | 3,623 µs |
| runner区間だけでの超過 | 118 | 1 |
| 実際の判断開始までの平均 | 870.3 µs | 717.5 µs |
| パルス要求までの平均 | 1,523.6 µs | 1,301.5 µs |

判断開始は solver audit の `start_us - sample_time_us`。
後段で記録する `entry_sample_age_us` と混同しない。
取得完了はホスト時刻であり、センサーの内部サンプリング時刻ではない。
パルス要求はソフトウェア上の要求であり、実電流の立ち上がりではない。

0.47.19 の残存超過124件中100件は、加速度も更新された周期だった。
1秒ごとの最大遅延として保存した150標本には、2.5 ms超過が85標本あり、
そのうち77標本では採用されたゼロクロス判断がなかった。
これは保存した代表標本の内訳であり、全124件の分類ではない。
したがって、探索・逆算をさらに削ることだけでは残りを説明できない。

最大3,623 µsの標本では、受信1,121 µs、派生値1,256 µs、MEKF後2,719 µs、
判断準備完了2,906 µs、全体終了3,623 µs。受信→終了の間に、IMU pollとの
重なりが1,421 µs、I/O呼び出しとの重なりが889 µsあった。
**重なりは経過時間であり、制御を止めたCPU時間ではない。**
このデータだけでフラッシュのキャッシュミスや割り込みを単独原因と断定しない。

0.47.19 = 36490177, 64151753, 166370865, 294812672, 387127557。

## 変更

MEKFの数値カーネルは既に `O2 / no-fast-math / IRAM` だった。
今回は周囲の通常更新に同じ速度優先の方針を限定適用する。

| 対象 | 変更 |
|---|---|
| 加速度からの派生値計算 | 関数をO2・内部RAMへ配置 |
| `updateFilterSeries` | MEKF呼び出し・比較入力準備をO2・内部RAMへ配置 |
| 姿勢スナップショット | コピーと制御用pitch抽出をO2・内部RAMへ配置 |
| 角度表示・現在角度の更新 | 3関数をO2・内部RAMへ配置 |
| 比較フィルターの実行 | `finishDeferredComparison` とpitch抽出をO2・内部RAMへ配置 |
| MadgwickのIMU更新 | 2つの `updateIMU` と `invSqrt` の宣言に同じ属性を付与 |

コンパイラーは通常の `-Os` より速度を優先できる。対象関数を内部RAMへ置くことで、
それらの命令取得はフラッシュキャッシュに依存しなくなる。ただし、呼び出し先の
数学ライブラリーや定数・データはフラッシュに残り得る。経路全体がキャッシュ停止中に
実行できるという意味ではなく、全超過の解消を保証するものでもない。

数値式・状態機械の実装本体は変更しない。Madgwickは固定した2.4.0のソース本体を
そのままビルドし、検証済みヘッダーの宣言だけに属性を付ける。
ソースとヘッダーのハッシュ検証、再ビルド時の同一性確認、不明な編集の拒否を行う。
既存の依存ファイルを無条件に書き換えるパッチではない。

MEKF、動的β、同じ標本の比較更新、全軸診断、足観測、ログを維持する。
推定・判断・比較・記録の順序、IMU 400/200 Hz、1 ms poll、コア・優先度、
3 ms補償、Q逆算、300 mA / 100 ms制限、10 ms stale STOPも同じ。
期限の起点・終点と超過判定は0.47.19から変えず、比較計算を期限外へ移さない。

## 検証と実機比較

- 実際の推定・表示メソッドと凍結した旧実装を32,000状態で比較。
  MEKF角度・クォータニオン・比較値が一致。準備から比較実行までのパルス変化7,750件も確認。
- 実際のMadgwick更新本体を `-Os` の参照クラスと、宣言にO2属性を加えたクラスで
  別々にコンパイルし、72,000回の更新を比較。両オーバーロード、β変化、加速度なし、
  静止、急回転、非有限入力、全軸角度・重力ベクトルが一致。
- 従来のMEKF、Q逆算、足校正、停止・取得、ログ、Web転送の回帰検証も実行する。
- ESP32実行ファイルで関数の実際のIRAM配置を検証。既存カーネルの16 KiB制限を維持し、
  追加対象には別途12 KiBの関数本体上限を設ける。定数領域を含む全体サイズはリンカーも検査する。

ホストでの数値一致とターゲットでのリンク検証は、実機上の処理時間の証明ではない。
書き込み後は同じ8°・30秒でまず1回、起動・測定・保存を確認後に計5回のRWLOGと足CSVを採る。
超過件数・最大・平均、判断開始時刻、各処理区間、取得異常、足観測率を0.47.19の5回と比べる。

0.47.19 の64151753は振幅の左右差が大きく、5–30秒のピーク誤差平均が約2.21°だった。
5回全体のピーク誤差平均は約0.825°で、旧版の約0.771°より改善していない。
起動時のゼロ基準にも約1°の差があるが、原因の確定には足りない。
処理時間の改善と振幅制御性能は分けて評価する。
