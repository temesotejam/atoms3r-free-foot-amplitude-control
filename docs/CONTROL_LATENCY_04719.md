# 0.47.19 IMU通信待ちと制御判断までの遅延

変更元：`c9b6229e4ecf051382695f25db94aa952ab532ee`（0.47.18）。2026-09-26。

## 確認した原因と変更

IMU取得はCore 1／優先度6、制御は同じCore 1／優先度4です。M5GFX 0.2.30のI²C読取りは、通信完了までフラグを確認し、`taskYIELD()`を呼ぶ方式です。取得側がReadyのままなので、低優先度の制御へ実行権を渡せません。前版5回では149,918回の確認処理の59.50%が新データなし、1回のポーリング全体は平均417.10 µsでした。これは割込みを含む経過時間で、CPU使用率ではありません。

0.47.19は起動時のM5UnifiedによるBMI270設定・ストリーム確認を終えてから、専用I²C1を解放し、ESP-IDF 4.4系の割込み完了待ちドライバへ一度だけ移管します。チップID・初期化状態・電源設定を再読取りして確認し、成功後だけ取得タスクを起動します。失敗時に旧方式へ黙って戻すことはありません。Rollerとカメラ起動時のSCCBはI²C0のままです。

既存の選択読取り（STATUS、更新されたセンサのDATAだけ）を保持し、M5Unifiedの換算・軸・タイムスタンプ処理もそのままです。I²Cは1 MHz、確認周期は1 ms、ジャイロ400 Hz／加速度200 Hzです。`i2c_master_write_read_device`はスタック上のコマンド列を使い、完了通知をキューで待ちます。その間は制御タスクを実行できます。転送ごとのヒープ確保は行いません。

注意：APIに渡す2 tickは異常時の厳密な2 ms上限ではありません。固定版IDFには、通知が来ないときにそれより長く待つ内部監視があります。制御側は独立して実行でき、既存の「IMU値が10 ms以上古ければ停止する」処理を残します。異常時の停止は、センサを外した実機試験まで保証したものではありません。

自律制御の測定中は、比較用Madgwickの入力6軸値とbeta、計測用のパルス状態を制御判断前に確定して保持します。MEKFと制御判断を先に実行し、同じ測定値のMadgwickをその直後、状態遷移・ログ保存・公開スナップショットより前に計算します。判断中にパルスが始まってもbetaを取り直しません。起動校正・START_SYNC・従来の別モードは従来の順序です。直立診断の加速度ノルムは、同じ測定値について取得後に計算済みの値を再利用します。

## 制御・観測の条件

必要Qと通電幅の計算式、MEKF、足の検出と校正範囲、3 ms補償、300 mA・最大100 ms、30秒測定、同期LED、ログ形式v51と既存列を維持します。比較計算も同じ加速度更新ごとに実行します。

処理順序・通信時間が変われば、実機でパルスが始まる時刻とその後の軌道は変わり得ます。ホスト上の同一入力検証は実機の制御性能や期限達成の保証ではありません。2.5 ms判定の終点は引き続きrunner終了で、後段へ移した比較計算と通常ログ保存も含みます。

## 追加する診断

RWLOGメタデータの`control_latency`へ保存します。全測定の段階別集計と、1秒ごとに完了時の古さが最大だった測定の詳細を残します。詳細は全測定・全超過の一覧ではありません。

| 項目 | 意味 |
|---|---|
| sequence / sample_us | ジャイロの測定番号とM5Unifiedの読取り後ホスト時刻 |
| poll_to_sample_us | その読取りを含むポーリング開始からホスト時刻まで |
| received_age / derived_age | キュー受信後／派生加速度計算後の古さ |
| mekf_age / control_ready_age | MEKF処理後／運動判定に入る直前の古さ |
| decision_age | 受理した中央通過について、通電量の判断を始めた時点の古さ |
| done_age | 比較計算・通常ログも含むrunner終了直後の古さ |
| poll_overlap… / io_overlap… | 受信後の区間に重なった取得処理／I²C API呼出しの経過時間 |
| polls_to_ready | 受信から運動判定前までに新たに始まったポーリング数 |
| io_calls_with_control_progress | I²C API呼出し中に制御の計測地点が進んだ回数 |
| valid_mask | 詳細行で有効な段階。中央通過でない測定のdecisionは無効 |

重なりはタスクの純粋なCPU時間や正確な中断時間ではありません。通信APIの区間には準備・割込み・復帰と待機が含まれ、制御と同時進行する部分もあります。`poll_overlap - io_overlap`もCPU時間と呼ばないでください。`io_calls_with_control_progress > 0`は通信呼出し中に制御が進んだ証拠ですが、0だけで制御が一度も実行されなかったとは判断できません。センサ内部の取得時刻や物理的なモータ反映時刻は今回の計測対象外です。

`control_work_profile.filter`は、今回から測定中の後段Madgwickを含みません。`madgwick`自身の区間は実計算時に測り、パルス分類は入力確定時の状態を使います。前版のfilter区間とそのまま足し引きしないでください。詳細配列は固定32行、測定中のJSON生成や動的確保はありません。

## 検証と次の実機比較

- 前版の実際の姿勢推定・表示関数を固定し、現行関数と32,000状態を比較。MEKF制御角度、比較Madgwick、beta、同一測定の表示値が一致。うち7,750回は準備と比較計算の間でパルス状態を変化させる検証です。
- 実際の通信ラッパーを模擬IDFで実行し、ポート制約、初期化失敗、チップ確認、後始末、通信エラー伝播、旧経路へ戻らないことを検証します。
- 時刻折返し、集計と詳細の対応、無効段階、実験間リセット、取得連番・バックログ停止、既存の幅計算と足観測・最大サイズのログ出力も検証します。
- `bash tools/test_runtime.sh`と、実機向けビルド・リンク確認を実行します。電気的通信、実機起動、遅延短縮量は実機ログで確認します。

最初は目標8°・30秒を1回行い、起動、MEKFと足観測、FINISHED、RWLOGと足CSVの保存を確認してください。問題がなければ同条件で合計5回。比較元は0.47.18の33194198、35277958、121289825、218642103、328637132です。全体超過533/60,713（0.878%）、最大5,582 µs、幅計算平均260.50 µs。電池電圧・姿勢・床条件の違いも一緒に確認します。
