# 0.47.8: 自律運転時の ESTOP と制御処理時間の診断

2026-09-24。対象は Free-foot Runtime V2 の統合リポジトリ。
旧 MEKF / 振幅制御 / カメラの固定済みリポジトリは変更しない。

今回の直接の停止理由は **IMU の制御側への受け渡し遅延が 10 ms を超えたこと**。
モータパルス中に遅延が増える傾向がある。0.47.8 では重複した姿勢診断計算を
再利用し、処理時間の内訳を記録する。特定の関数が主因とはまだ断定できず、
実機で ESTOP が解消したことも未確認である。

## 入力と整合性

- 入力: `energy_control_autonomous_run_1_52231331.rwlog`
- サイズ: 194,501 bytes、RWLOG v51、通常サンプル 358 行。
- SHA-256: `aad0d536fef0bbeeb527def4b887cf8011610c31d1960c42d66c48ad7f212a56`
- CRC32: 保存値・再計算値ともに `4196194591`。区間境界とファイル長も一致。
- START_SYNC 239 行、RUNNING 119 行。約 5 秒の開始同期後、約 0.77 秒で停止。
- 足観測のリビジョンは `freefoot_runtime_v2_0477`、校正値も 0.47.7 と一致。
  旧版のルート `firmware_revision` は 0.47.0 の固定文字列だったため、これだけで
  書き込み版を判別できない。0.47.8 から実際の `RUNTIME_VERSION` を出力する。

主要数値と出典のハッシュは
[`tools/fixtures/estop_52231331_summary.json`](../tools/fixtures/estop_52231331_summary.json)
に保存した。元の添付ファイルは変更していない。

## 確認できた停止経路

`v46n_imu_acquisition.first_fault` は次の値を記録している。

| 項目 | 値 |
| --- | --- |
| fault_reason | `imu_delivery_backlog_over_10ms` |
| age_us | 10,284 us |
| delivery_age_limit_us | 10,000 us |
| first_fault.time_us | 58,005,346 us |
| first_fault.sample_us | 57,995,045 us |
| first_fault.queue_depth | 5 |
| first_fault.state_id | 3 / RUNNING |
| Web STOP 要求 / 消費数 | 0 / 0 |

`src/imu_manager.cpp` の順次受信処理が、受け渡し時の古さを検査して fault を
ラッチする。`src/main.cpp` が acquisition unhealthy を検出し、
`imu_acquisition_overflow_backlog_or_stale` で非常停止を要求する。
`time_us` と `age_us` は別の読時計時点なので、単純な差は完全一致しない。

最終通常行はまだ RUNNING、パルス 3、指令 -300 mA、実測 -165 mA だった。
これは停止要求の前の行であり、「停止後も -300 mA を指令していた」という
証拠にはならない。今回の RWLOG には停止状態の通常行がないため、0.47.8 で
停止後の状態をメタデータにも追加した。

## 遅延が発生した条件

計測区間の IMU 取得は 313 件、受け渡し監査は 309 件。取得間隔は平均
2,469.534 us、最大 4,112 us、5 ms 超は 0 件だった。受け渡し監査は
古さ検査より前に件数を加算するので、309 件すべてが正常消費されたとは扱わない。
キュー上限 32 に対し最大 5、ドロップ・シーケンス抜けはともに 0。
ドライバ呼び出しは 771 回、失敗は 0 回だった。

RUNNING の保存行をパルスの有無で分けると、次の差があった。

| 保存行の条件 | 行数 | IMU sample age 平均 | 最大 |
| --- | ---: | ---: | ---: |
| パルス出力なし | 24 | 1,883.667 us | 6,131 us |
| パルス出力中 | 95 | 6,238.505 us | 11,015 us |

これは保存時点の古さであり、受け渡し時点の 10 ms 検査とは異なる。
また出力中は通常時よりログ周期が短いため、全時間に対する平均ではない。
パルスは計測 0 ms / 368 ms / 707 ms に開始し、いずれも設定幅は 100 ms。
遅延は出力中に増え、出力の合間に減る傾向だった。3 回目の終了予定前に停止した。

既存の制御完了監査でも、取得から runner 復帰までの 2,500 us 予算を
309 件中 142 件が超過し、最大 11,162 us だった。一方、2 回のパルス決定処理は
1,201 us / 1,837 us、その中の探索は 232 us / 684 us。
単発の長大な探索だけで説明する証拠はなく、出力中の継続的な処理負荷や
タスクの割り込みを含めて切り分ける必要がある。

既存 `max_path_us` は runner 復帰までで、その後の表示用スナップショットの
作成・公開を含まない。直立診断は同じ加速度値から三角関数・平方根を繰り返し
計算しており、この重複を整理した。ただし、これが主要因という計測証拠はまだない。

足観測は 58 フレーム（開始同期 50、計測中 8）。両足の検出・校正範囲・
タイムスタンプは全件 valid、観測バッファの overflow は false。
このログは足の認識失敗による停止を示していないが、動作中の角度精度や
マーカの取り違えがないことを独立に証明するものでもない。

1 時間以上の待機動作が継続したという前回の結果と、今回の自律運転中の
遅延は両立する。待機中にはない制御・パルス中の記録負荷を確認する試験である。

## 0.47.8 の変更

1. 加速度・ジャイロのシーケンスが同じ間は、直立診断の幾何計算を再利用する。
   センサの健全性、データの古さ、直立保持時間は従来どおり毎ステップ検査する。
2. runner 内の加速度角度の重複計算を、ImuManager がすでに計算した同じ値に置き換える。
3. 計測中の処理時間を `control_work_profile` に記録する。
4. `terminal_state` に書き出し時点の状態名、エラー、モータ指令・実測電流、
   スナップショット時刻を保存する。これは fault 発生瞬間の記録や、
   モータ側でゼロ電流指令を受理したことの確認ではない。
5. ルート `firmware_revision` を実際のビルドバージョンに合わせる。

IMU の取得周期・順序、10 ms の保護条件、制御モデル、3 ms の補償、
300 mA / 100 ms のパルス制限、足の校正値・認識方法、ログ周期は変更していない。
RWLOG のバイナリ行形式も v51 のまま。

### 新しい処理時間の読み方

各ステージは `count`, `sum_us`, `mean_us`, `max_us` を記録する。

| ステージ | 測定対象 |
| --- | --- |
| owner_iteration | 制御の 1 周。runner 復帰後のスナップショット作成・公開も含む |
| service | STOP 処理、取得コンテキスト更新、高速サービス、動的 beta コンテキスト |
| imu_delivery | IMU の受信・消費処理。受信待ちを含む |
| pose_guide | 直立診断・保持時間の更新 |
| filter | 姿勢フィルタ群の更新 |
| angle_display | 表示角度の作成 |
| current_roll | ロール状態・静止状態の更新 |
| motion | ゼロクロスの診断と自律運転の制御処理 |
| log_row | 通常ログ行の作成・保存 |
| snapshot | 表示用スナップショットの作成 |
| publish | スナップショットの公開と実行状態の診断更新 |

- `pulse_on` / `pulse_off` は各ステージへの進入時のパルス状態で分類する。
  途中でパルスが開始・終了する周回では、ステージごとの所属が異なる場合がある。
- 上位の 1 周と下位ステージは入れ子なので、合計して CPU 使用時間にしない。
  時間は他タスクによる中断を含む実経過時間であり、CPU 占有時間ではない。
- owner / snapshot / publish は周回開始前の公開状態が RUNNING の場合に記録する。
  停止へ遷移する最後の周回を含み、START_SYNC からの最初の遷移周回は含まない。
  個別 runner ステージは進入時に RUNNING の場合に記録する。
- 測定中は固定長の整数カウンタだけを更新する。JSON 生成は停止後の書き出し時。
  次の運転開始時にリセットし、停止後の待機処理は集計に追加しない。
- 計測自体にも少量の負荷がある。このビルドの結果で改善量と残る負荷を判断する。

## 検証と実機での次の確認

`bash tools/test_runtime.sh` のホスト回帰テストに、シーケンス折り返し・
ジャイロのみ更新・無効値を含む診断値の同値性、時刻折り返し、パルス別集計、
停止後の集計固定、terminal metadata の実出力確認を追加した。
既存の IMU 取得、MEKF、足画像、WebUI、CRC、最大イベント数の RWLOG も対象とする。
ホストテストや実機向けビルドの成功だけでは、実時間の処理予算達成を確認できない。

実機では [Web Flasher](https://temesotejam.github.io/atoms3r-free-foot-amplitude-control/)
で **0.47.8-control-work-profile** を書き込み、通常の直立ゼロを完了後、
前回と同じ足を固定しない条件・設定で 30 秒の自律運転を 1 回行う。
完走しても ESTOP になっても、その RWLOG を保存する。
終了状態の診断 JSON もあれば併せて保存する。外部動画撮影は今回の必須条件にしない。

次のログで見るのは、停止理由、最大受け渡し遅延、パルス有無による処理時間の差、
足観測の継続、停止後の指令値である。自由に動く足の対地絶対角度を、
MEKF だけを正解として評価する試験ではない。
