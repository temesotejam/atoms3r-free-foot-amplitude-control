## 今回外す処理と原因判断の限界

コードを確認すると `RuntimeDiag::beat()` が各タスク自身のスタックを
`uxTaskGetStackHighWaterMark(nullptr)` で約 1 秒ごとに走査していた。
制御側は `publish` 区間、優先度 6 の IMU 取得側は `poll_total` の計時終了後に実行する。
取得側の走査時間は従来の `poll_total` には含まれず、制御側の割り込み待ちに
現れる可能性がある。

今回の `publish` は加重平均 22.484 us に対し最大 2,247 us。他の短い区間にも
ms 単位の最大値がある。しかし、各最大値とスタック走査時刻を対応付ける記録はない。
**スタック走査は除去可能な負荷だが、すべての超過の原因とは断定しない。**
ログ作成平均も 356.791 us、うち変換平均 278.487 us、保存平均 37.774 us であり、
フィルタ・ログ・ポーリングの負荷は残る。各区間は入れ子かつ実経過時間なので、
単純に足したり、純 CPU 使用率に換算したりしない。

## 0.47.15 の変更

- 制御タスクは `next.running`、IMU 取得タスクは既存の同期取得コンテキストを使い、
  開始同期・測定・試行間休止・終了同期の間、定期スタック走査を保留する。
- 保留中も heartbeat・処理位置・詳細値は更新し、最後のスタック診断値を保持する。
- 停止後、期限が来ていれば各タスク自身の最初の idle beat で走査を再開する。
  他タスクの動作中のスタックを外から走査する方式にはしない。
- USB に `USBDBG,stack_scan,control` / `imu` を追加し、許可状態・回数・最終時刻・
  値の古さ・直近／最大走査時間を出す。走査時間は中断を含む実経過時間である。
- RTC 診断の構造体と識別子、スタックオーバーフロー保護、MEKF・比較推定・足観測、
  校正値、制御則、ログ内容・周期、2.5 ms 完了監査と 10 ms 停止条件は維持する。

[Espressif の API 定義](https://docs.espressif.com/projects/esp-idf/en/v4.4/esp32s3/api-reference/system/freertos.html)
では、この値はタスク開始以来の最小残存スタックである。したがって同じタスクが
停止後に走査しても、それまでのスタック使用の痕跡を調べられる。
ただし運転途中でリセットした場合、保存済みの診断値は直近走査時の値のままであり、
未走査期間の最低値を RTC 記録から復元できるわけではない。

検証では、起動直後の保留、40 秒間の callback 非実行、停止直後の再開、1 秒周期、
短い運転・ESTOP 後の期限判定、32 bit 時計の折り返しを確認する。
既存の推定・取得・制御・転送・足観測・全ログ行の互換性検証も実行する。
ESP32-S3 の実ビルドと公開後のバイナリ照合を経て配布する。
これらは実機の速度改善や 2.5 ms 期限達成の証明ではない。
