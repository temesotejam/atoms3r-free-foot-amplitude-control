# 0.47.3：傾斜時の足マーカー未検出と上下探索

## 実機データから確定したこと

0.47.2に更新後、ユーザーから「WebUIは安定して更新されるが、傾くと左右の足角度が消え、
直立では認識する」と報告されました。続く4件の診断JSONは次の状態です。

| 診断ファイル | 直立からの姿勢誤差 | 右X / 有効 | 左X / 有効 | 画像年齢 | 実測fps |
|---|---:|---|---|---:|---:|
| freefoot-diagnostics.json | 2.5554° | null / false | 109.097 / true | 24.0 ms | 10.0310 |
| freefoot-diagnostics (1).json | 20.6740° | null / false | null / false | 101.7 ms | 10.0116 |
| freefoot-diagnostics (2).json | 5.1248° | null / false | null / false | 102.9 ms | 10.0199 |
| freefoot-diagnostics (3).json | 2.1547° | 170.4572 / true | 113.2923 / true | 73.8 ms | 10.0295 |

全件で `zero_ready=true, zero_samples=22, frame_timestamp_valid=true, failures=0`。
ゼロ点は右168.5885、左110.8449で保持され、内部空きヒープは約123.9 KBです。
カメラ初期化・受信・XCLKも有効です。最後のJSONで左右とも復帰しています。
この区間の角度消失の直接原因はマーカー未検出です。ゼロ点の解除でも、画像の500 ms期限切れでも、
校正X範囲外の非表示でもありません。`frames=0` は測定ログの記録枚数で、撮影停止を意味しません。

ただし画像自体は含まれていません。上下移動、遮蔽、明暗、別の白い物体への反応のどれが
実機の未検出を起こしたかは、これらのJSONだけでは確定できません。

## 旧検出器で再現した弱点

右はY={58,62,66,70,74}、左はY={152,156,160,164,168}の5本しか測定していませんでした。
背景用の3本も固定です。高さ21 px・幅21 px、背景30・白230の合成画像を使い、
元の `WhiteMarker1DTracker` をそのまま実行すると、上下16 pxの移動で検出が失われます。
左は下へ12 pxでも背景走査線へ白が入り、明暗差が相殺されます。
Xだけを動かした場合は検出と角度計算が続き、校正範囲外でも範囲フラグだけがfalseになります。

## 変更内容

- 最初に従来と同じ高さ・同じX演算を実行し、有効ならその結果を採用します。
- 未検出時にマーカー5本と背景3本を一緒に上下へ動かし、±32 pxを4 px刻みで探索します。
  各足最大17テンプレート。両足のマーカー走査領域は重ならず、全参照行が画像内に収まります。
- 回復候補は「判定通過、ピーク明暗差、白領域の重み」の順で比較し、同点なら基準高さに
  近い候補を残します。同じ距離の上下が完全同点なら先に調べる上側です。
  明暗差55・重み150などの閾値を下げず、過去の検出位置も流用しません。
- 作業配列は従来同様に320整数×2。各評価で再利用し、再帰・動的確保・画像コピーは行いません。
  追加CPU負荷は実機の `processing_us / processing_max_us / fps` とUSBのタスク生存情報で確認します。
- 画像取得失敗、明暗差不足、白領域不足、画像時刻の無効、ゼロ点待ちを区別します。
  足が未検出なのに「IMUの初期化を待っています」と案内する表示も修正しました。
- 制御、MEKF、Roller通信、電流上限、LED同期、30秒測定、ログ転送とカメラスタック修正を継続します。
  足角度は引き続き観測用です。

## 診断とログ

診断JSONの `foot` に次を追加しました。フレーム単位の位置・品質・理由・探索数は
RWLOGの `foot_frames` と足角度CSVにも保存します。RWLOG v51のサンプルバイナリ配置は変えません。
旧RWLOGの変換では追加列が空欄になります。

| フィールド | 意味 |
|---|---|
| `detector` | `sparse_rows_vertical_v1` |
| `right_reason`, `left_reason` | `detected`, `no_frame`, `low_contrast`, `low_weight`。画像内検出の判定で、角度の有効フラグとは別 |
| `right_scan_y`, `left_scan_y` | 採用した走査テンプレート中心Y。実測したマーカーのY重心ではない。未検出ならnull |
| `right_contrast`, `left_contrast` | 選んだ候補のピーク明暗差。未検出時も最良候補の値を残す |
| `right_weight`, `left_weight` | 選んだ候補の白領域重み |
| `right_templates`, `left_templates` | 0=画像なし、1=基準高さで認識、17=上下探索を実施。17だけで検出成功とは判断しない |
| `frame_valid` | 完全な320×240グレースケール画像が今回届いたか |
| `sequence`, `captured_frames` | 起動後の取得試行連番、完全画像の累積枚数 |
| `right_marker_failures`, `left_marker_failures` | 完全画像内で各マーカーが未検出だった累積回数。画像取得失敗は含めない |
| `processing_max_us` | 起動後の左右画像解析処理時間の最大値。画像待機時間とは別 |

メタデータには探索範囲・刻みと `scan_y_semantics` を記録します。
校正係数0.167779119 / 0.162645305 deg/pxは従来値です。上下移動した姿勢での角度精度は
まだ検証していないため `vertical_recovery_angle_accuracy_validated=false` と明記します。
新しく見つかった位置が正しい足マーカーか、係数がその姿勢でも妥当かは実機画像・角度との比較が必要です。
画角外、探索範囲外、遮蔽、白い背景や似た物体は解決を保証しません。

## 検証

`tools/test_foot_tracking.cpp` は、±32 pxの全整数移動・複数X・両足の逆方向移動、
反対側マーカーだけの画像、斜めの白帯、基準行への復帰、一様背景、低コントラスト、
小さすぎる白領域、範囲外、画像欠落での過去値不使用を検証します。
既存のゼロ点保持、符号、校正範囲フラグも検証します。
ブラウザテストは傾斜中の表示、左右別の理由、画像時刻・鮮度・終了後最終値を検証します。
実シリアライズした最大イベント＋768足フレームをCRC検証・CSV変換し、追加診断の保持と旧形式互換を確認します。
ESP32-S3のビルド、SDKカメラのスタックラッパー呼び出し、公開SHAと4バイナリのハッシュはCIで検証します。
これらは実機での回復・処理時間・測角精度を証明するものではありません。

ローカルの全ホスト検証は通過し、最大メタデータは1,385,563 bytesで2 MiB枠内でした。
検出器はAddressSanitizer/UndefinedBehaviorSanitizerでも通過しています。
実行環境がptrace下のためLeakSanitizerは利用できず、メモリ境界・未定義動作の検査だけを実行しました。

## 次の実機確認

[Web flasher](https://temesotejam.github.io/atoms3r-free-foot-amplitude-control/)の
**0.47.3 足マーカー上下探索版**を書き込み、最初は測定開始前に左右のゼロ点を確定します。
直立→角度が消えていた傾き→直立と動かし、各姿勢で診断JSONを保存します。
`right/left_reason=detected`、探索時の `scan_y`、フレーム鮮度、処理時間を比べます。
基準高さは右66・左160です。上下探索で回復した場合も、実際の足の向きと角度の符号・変化を確認します。
未検出が続く場合はそのJSONとマーカーの見え方が分かる画像を使い、探索範囲・遮蔽・明暗を判定します。
確認後に30秒測定、RWLOGの取得・再開とCSV保存まで進めます。
