# 取り付け方向・機体座標・足角度の監査

調査日: 2026-09-24

対象ファームウェア: `de7ebb4fb271d15215e0dad4ca0c6ad7d3048fd7`、0.47.3-adaptive-markers。
機体参照: `rw-walker-digital-twin` の `adcd80a2dfe6acdd6602adb0e6ef468e4e81fce7`。
この文書は調査結果であり、実機で確認した新しい軸校正値ではない。

## 1. ユーザー確認を機体の基準にする

今回の追加確認:

- ATOMS3R-CAMのカメラは機体が直立したとき真下を向く。
- USB-Cの書き込み口は機体を後ろから見て左側にある。これは機体自身の左側と一致する。

過去の確認:

- カメラとIMUは胴体に固定されている。
- 白四角マーカーは足の甲に固定されている。
- 脚・足には膝関節と足首関節がない。
- 画像上段Marker Aは右足、下段Marker Bは左足。
- 最新の手動試験では、両足を地面に直立させて置き、胴体を**前後に**傾けた。
- ユーザーの追加確認により、今回比較していたMEKF表示は左右揺動用と整理する。前後傾斜との値の差は、この試験でのMEKF異常の根拠から外す。

カメラ方向とUSB側面方向という直交する二方向により、筐体の三次元の取り付け姿勢は概ね決まる。カメラの高さ、関節からの距離、微小な取り付け誤差は、この二情報だけでは決まらない。

## 2. 公式図・センサ生値・API値・MEKFを混同しない

### 2.1 公式の筐体上の軸

M5StackのATOMS3R-CAM公式IMU方向図では、+Zはカメラ面から外向き、+YはUSB側面の反対向き、+XはUSB側面と平行である。
これを今回の取り付けへ回転すると、公式図の軸について次が導ける。

| 公式図の軸 | 機体上で向く方向 |
|---|---|
| +X | 前 |
| +Y | 右 |
| +Z | 下、カメラの光軸方向 |

これは**公式図の矢印と筐体の対応**である。図の軸名を、以下のAPIの出力名へ無条件に置き換えない。

### 2.2 M5Unified 0.2.18の処理

上流の`IMU_Class.cpp`を確認した。AtomS3R / AtomS3RCam / AtomS3RExtとして初期化された場合、加速度とジャイロの両方に`axis_order_yxz | axis_invert_y`が適用される。

チップのレジスタ値の軸をS、`getImuData()`の出力軸をUとすると、軸対応は:

```text
U.x =  S.y
U.y = -S.x
U.z =  S.z
```

上記は軸変換部分だけを示す。実際の値には単位換算とオフセット補正も入る。

現在の`imu_manager.cpp`は`M5.Imu.begin(&M5.In_I2C, M5.getBoard())`で初期化し、`getImuData()`を`ax_g / ay_g / az_g`と`gx_dps / gy_dps / gz_dps`へコピーする。したがって、このファームウェアで「raw」と呼ばれる値も、レジスタ軸のままとは限らない。

タイミング用BMI270パッチはレジスタ読み出しを最適化するだけで、この後段の軸変換を回避していない。旧`atoms3r-foot-angle-tracker`も、AtomS3RCamを明示して同じAPIを使う。

### 2.3 MEKFへの追加変換

`experiment_runner.cpp`はUにさらに次を適用する。

```text
MEKF accel = (-U.ax, +U.ay, -U.az)
MEKF gyro  = (-U.gx, +U.gy * 0.908911, -U.gz)
```

幾何学的にはY軸回り180°の回転であり、ジャイロYには別途感度補正がある。UIの胴体角は、このMEKFのEuler角のうち`pitch`を、状態に応じた基準・遅延補償を経て表示する。

**未確定点:** 公式の製品図は、図の軸がレジスタ軸SかAPI軸Uかを明示していない。この図へM5Unifiedの変換を重ねてよいかは、資料だけでは最終確定できなかった。

図=Sとした作業仮説ではUは「右・後・下」、MEKFは「左・後・上」となり、MEKFのY回りpitchは機体の左右揺動に対応する。図=Uなら役割が90°異なる。ここを推測で決めて制御軸や補正係数を変更しない。

また、実機の診断JSONには認識されたboard IDがない。今回の取得資料から、実行時の認識結果まで確認できたとはしない。

## 3. 機体資料から分かる機構と、仮定だった寸法

Digital Twinの正式な参照座標は**X右・Y前・Z上**。旧研究メモの「X前後・Y左右」とは異なる。記号の名前を転記せず、物理方向で対応させる。

| 機構・運動 | Digital Twinの軸・構造 | 出典上の位置づけ |
|---|---|---|
| 左右に揺れる運動 | Y、前後方向の軸回り | 主なモデル対象 |
| リアクションホイール | 軸Y、回転面X-Z | モデルの機構仕様 |
| 脚の前後振り | ヒンジ軸X、左右方向の軸回り | モデルの仮定。実機関節の完全CADは未取得 |
| 左右の脚・足 | 左右別剛体、各側の脚と足は同一剛体 | 膝・足首なしというユーザー確認と整合 |

足の前後振りと、RWで励起する左右揺動は別の回転自由度である。手で「本体を傾けた」ときも、どちらの軸回りかで比較すべきIMU成分が変わる。

| 参照値 | 数値 | 根拠・限界 |
|---|---:|---|
| 足裏円弧の外半径 / 内半径 | 150 / 148.5 mm | 参照モデルではCAD由来 |
| 足裏の前後幅 | 56 mm | 同上 |
| 足裏の左右領域 | 中心から各側5〜45 mm | 同上。中央の空隙は10 mm |
| 総質量 | 199.7 g | 過去の参照機体の測定値 |
| 重心高さ | 128 mm | 実験由来の作業値 |
| RW外径 | 約60 mm | 概算 |
| RWの追加重り | 約6.8 g × 4、軸から約26 mm | 概算。52 mmは配置直径 |
| 関節高さ120 mm、本体48×38×60 mm、RW高さ160 mm | — | 明示的にassumed。実物寸法として使用しない |

これらは機構理解の根拠にできるが、現在のカメラ高さやマーカー位置を埋める値には使えない。全体CADと電子機器・固定具の配置は参照モデルにも未再現と記載されている。

## 4. カメラと足マーカー

旧校正側と現在側のカメラ設定はともにGC0308、QVGA 320×240、`vflip=1 / hmirror=0`。この統合時に反転設定が変わったという証拠はない。

上段A=右足、下段B=左足という実機確認、および旧直立画像で両者のXが約170〜175だったことから、直立付近では画像の縦方向が概ね機体の左右、横方向が概ね前後に対応すると考えられる。画像右が機体の前か後かという符号は、実際の画像と既知方向の動きを対応させて確定する。

旧校正と現在の計算対象は**胴体に対する足の相対角**である。同一軸・同一符号で表す平面運動では:

```text
足の対地角 = 胴体の対地角 + 足の胴体相対角
```

足を対地固定して胴体だけ動かせば、足の対地角は一定でも、胴体相対角は変わる。両足の実際の姿勢が同じなら、正しく校正された左右の相対角も概ね一致する必要がある。

この式は、別軸のEuler角同士へそのまま使えない。三次元では足姿勢と胴体姿勢を回転行列またはクォータニオンで合成する。現在の相対角にUIのMEKF pitchを足すだけでは、対地角を正しく得られるとは限らない。

一方、胴体と足が一緒に剛体回転し、相対姿勢が変わらなければ、胴体に固定されたカメラ内での足位置も変わらない。相対角を一定にするための無条件のIMU差し引きは不要である。

透視投影は`u=cx+fx*Xc/Zc, v=cy+fy*Yc/Zc`である。左右で深さやマーカー位置が違えば、同じ角度に対するピクセル移動も同じとは限らない。1本の横座標だけを固定係数で角度化する校正は、関節運動の経路と取り付けが変わると一般化できない。Y方向の探索範囲を広げることは検出継続を助けるが、この幾何の問題は解決しない。

## 5. 最新の異常との関係

既に読んだ`freefoot-diagnostics (4).json`と`(5).json`を再解釈する。

| 項目 | 直立側 | 傾斜側 |
|---|---:|---:|
| 直立基準の加速度方向からのずれ | 0.7613° | 20.6728° |
| UI胴体MEKF | 0.4552° | 1.1949° |
| 右足の相対角 | 0.1488° | 22.9133° |
| 左足の相対角 | 0.6355° | 10.8921° |
| 右マーカーX | 170.8739 | 35.1925 |
| 左マーカーX | 97.7293 | 34.6681 |

### 5.1 20°と1°の差だけではMEKF異常と判定できない

直立方向のずれは、保存した加速度方向との**符号なし三次元角度**。UIはMEKFの一つのEuler成分であり、量が違う。

現在の初期姿勢計算式で確認すると、API座標のX回りへ20°傾けた静止姿勢は、重力方向のずれ20°、MEKF roll約−20°、MEKF pitch約0°を正常に生む。Y回りなら、重力方向のずれ20°、roll約0°、pitch約20°になる。

これは軸を区別する必要性を示す計算例である。その後ユーザーが今回の操作は前後傾斜であり、MEKF表示は左右揺動用と指摘した。この説明と20°対1°という結果は整合するため、今回の実装ではMEKFの軸と校正を変更しない。最新JSONに加速度・ジャイロの3成分とクォータニオンがないことは、細かな符号の実測確定の限界として残る。

過去にも軸の不一致が記録されている。Digital Twinに保存された2026-08-24 V62監査では、14:00のrunは動画角速度とgyの相関が+0.994、同日の18:51 passive runはgxが対応した。IMU取得コードは同一で、取り付けや動画基準の変化は未解決とされた。過去の「gyで合った」を全組立・全運動に適用しない。

### 5.2 左右約12°差は独立に残る

今回の左の起動時ゼロは101.6366 px、旧校正の左ゼロは174.843512195 px。差73.206912195 pxは、現係数0.162645305 deg/pxで**11.906760562°**に相当する。傾斜時の左右差12.0212°に近い。

この一致は、左のゼロ取得時と傾斜時で違う明部を選んだ可能性を強く検討する理由になる。既存のsynthetic画像試験でも、実装の通常Y優先とフォールバックで、同様の右22.99°・左10.90°を再現できた。ただし実機画像がないため、実物での誤認識と、マーカー配置・校正条件の変化を最終的に区別したものではない。

`detected`はコントラスト・重み閾値を通過したことを表し、正しい白四角の同一性を保証しない。傾斜側のX約35は、左右とも旧校正の観測範囲外でもある。

0.47.4ではこの再現経路へ対処し、同一フレームの検出画像・候補情報の保存を追加した。変更内容と実機確認手順は[マーカー識別・ゼロ点確認](MARKER_IDENTITY_0474.md)を参照する。以下には今後の校正・計測方針も含み、全項目を0.47.4で実装したという意味ではない。

## 6. この調査から導く実装・計測方針

1. 「左右揺動」「前後傾斜」「足の胴体相対角」「足の対地角」を別の物理量として定義する。制御・表示・校正で同じ軸と符号の定義を使う。
2. センサレジスタ軸、M5Unified API軸、MEKF軸、カメラのピクセル方向の対応を一箇所に記録する。実機の既知方向の静止傾斜で最終確認する。
3. 同一時刻に近いカメラ画像・検出枠・候補位置・選択理由と、API加速度/角速度3成分・全姿勢・board IDを観測可能にする。既存JSONの集計値だけでは対象同一性と軸を確定できない。
4. 起動時ゼロを、直立判定だけで確定させない。IMUが判断するのは胴体の直立であり、両足の中立姿勢や白四角の同一性は別に確認する必要がある。
5. 左右の候補を継続追跡し、別の白い領域への飛び移りや候補競合を品質低下として扱う。ゼロを旧数値へ固定する、左だけ係数を増やす、といった二点合わせでは検出の問題を解決できない。
6. 確定した関節軸と画像経路に対して校正する。必要なら二次元位置や四角の形状・透視投影を利用する。部品寸法が不明な状態で、シミュレータの仮定寸法から実機の角度係数を作らない。
