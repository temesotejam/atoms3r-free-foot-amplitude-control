## 0.47.16 の変更と検証範囲

### 計算コードの配置

MEKF の予測・加速度補正・制御ピッチ抽出とその補助関数、ログ変換器と共通量子化関数を
ESP32 の IRAM に配置する。計算式・丸め・共分散更新・コンパイラの最適化方針はそのまま。
頻繁な呼び出しで命令キャッシュの入れ替わりによる待ちを減らすことを狙う。
量子化はヘッダーのインライン定義から単一の `.cpp` 定義へ移し、変換器から直接呼ぶ。
最初の候補ビルドではインライン IRAM 関数のリテラルが flash 側に残るリンクエラーが
検出されたため、この構成で関数本体とリテラルの配置を揃える。

[Espressif の ESP32-S3 / IDF 4.4 性能ガイド](https://docs.espressif.com/projects/esp-idf/en/v4.4/esp32s3/api-guides/performance/speed.html)
は、小区間の時間がバイナリ配置とキャッシュに左右されること、頻繁な関数の IRAM 配置を
説明している。ただし今回のログでキャッシュミスを実測したわけではない。
IRAM は内部メモリを使い、他用途の空きを減らす。リンク済み ELF で必要な関数と残った
補助関数が実際に IRAM に入り、対象の関数本体合計が 16 KiB 以下であることを検査する。
この上限はリテラルや SDK 全体の IRAM 使用量を含まない。
既存のログ変換器 4 KiB 上限も継続する。

外部数学関数や定数データは flash に残り得る。経路全体がキャッシュ無効時に実行可能と
いう主張ではなく、割り込みや高優先度の IMU 取得による待ちも解消するわけではない。
なお使用中の Arduino-ESP32 2.0.16 の
[qio_opi 設定](https://github.com/espressif/arduino-esp32/blob/2.0.16/tools/sdk/esp32s3/qio_opi/include/sdkconfig.h)
では CPU 240 MHz、lwIP は Core 0 固定。ネットワークタスクが Core 1 を自由に使うという
一般的な設定を今回へ当てはめず、タスクのコアと優先度は変更しない。

### 弱い候補の確認

直近 0.5 秒以内に追跡できていて、次の条件をすべて満たす候補に、既存の 3 フレーム確認を適用する。

- X が 20 px 以上、走査帯の Y が 16 px 以上変化する。
- コントラストが直前の採用値の 50% 未満になる。
- 検出の重みが直前の採用値の 10% 未満になる。

確認中は `reacquiring` とし、以前の足角度を新しい実測値として出さない。
本来の位置に強い候補が戻れば即座に採用し、弱い候補も継続して確認できれば再捕捉する。
明瞭な位置変化や、位置が変わらない明るさの低下は即時採用を継続する。
受け入れ範囲外でも強い候補や確認済み候補は元どおり値と範囲外フラグを出す。

供給済み 7 本の足 CSV（32653719、42183521、33554009、53979692、53514900、47136279、
55522052、合計 2,370 行）の採用候補情報に条件を当てると、対象は今回の右 sequence 601 のみ。
これは保存された候補情報の照合であり、画像からの完全な再検出やマーカー正解の検証ではない。
合成画像では、弱い候補の初回保留、元の位置への即時復帰、3 フレーム後の再捕捉、強い移動、
同位置の暗化、上下の探索・別ピーク・ゼロ校正を確認する。

全 posterior と共分散の差分検証、24,000 ケースの全 258 バイトのログ比較、
2,548,692 ケースの量子化境界比較、既存の取得・制御・転送・WebUI の検証も実行する。
実機での処理時間短縮と誤認抑制は未確認である。
