# 0.47.4: 足マーカーの識別、ゼロ点の品質、画像付き診断

対象: `0.47.4-marker-identity`。前版: `de7ebb4fb271d15215e0dad4ca0c6ad7d3048fd7` / 0.47.3。

## 症状と判断

ユーザーの試験は、両足を地面に直立させたまま、胴体を前後に傾けたもの。
MEKFの画面表示は左右揺動用であり、重力方向のずれ20.67°とMEKF表示1.19°は
異なる量である。この差を今回のMEKF異常の根拠にしない。
画面には「胴体の左右揺動 · MEKF」「左右足角度 · 胴体に対する相対角」と明記する。
足の対地角が一定でも、胴体が動けば胴体相対角は変化する。

一方、左右の相対角22.9133°と10.8921°の差は別に残る。左の起動時ゼロは
101.6366 pxで、旧校正の174.8435 pxから73.2069 px離れている。
この差は現係数で11.9068°に相当し、観測された左右差12.0212°に近い。
直立時と傾斜時で別の白い部分を選んだ可能性がある。

0.47.3では通常の走査行で候補が見つかると、他の高さの探索を省略していた。
弱い別候補を左のゼロに取り、その後、傾斜で通常行から外れた際に本来の白四角へ
切り替わる合成画像を作ると、右22.99°・左10.90°という差を再現できた。
これはコードで確認した失敗経路であり、実機画像なしに物理的原因を確定したものではない。

## 検出とゼロ点

- 各足で、従来と同じ5本の観測行・3本の参照行を±32 px、4 px刻みの全17位置で比較する。
  通常行の候補だけで探索を打ち切らない。上段A=右足、下段B=左足の探索帯は分離する。
- 横方向の白い連続領域ごとに重心を計算し、別の明部を一つの重心へ混ぜない。
  幅4〜72 px、従来のコントラスト55・基線35・重み150の条件を満たす候補を扱う。
- 近接する高さで同じ領域を見ている候補は統合する。最大24候補を固定配列で保持し、
  超過時や有力な競合候補がある場合は`ambiguous`として角度を無効にする。
  競合比の閾値は0.82。候補数は全探索帯で統合後の数、競合比は追跡ゲート内の上位2候補の比。
- 500 ms以内の追跡位置があれば、X方向80 px、走査Y方向32 pxを超える移動は採用しない。
  適合候補内でコントラストと小さな近接優先度を比較する。
  記憶期限後は、3フレーム連続して位置が整合した候補を再捕捉する。
  未検出時に古い角度を有効値として保持することはしない。
- ゼロ点は胴体の静止・直立、両足の有効な検出、途切れない2秒以上かつ15枚以上を要求する。
  各足の候補が旧中立位置から±35 px以内であり、取得中の各足のXの最大−最小が4 px以下であることも必要。
  条件から外れたら取得をリセットし、画面に理由を表示する。
- 左右のゼロは、その起動での実測平均を別々に保存する。上記±35 pxは妥当性の判定範囲であり、
  ゼロを旧定数に固定する処理や左右を同じ角度へ合わせる処理ではない。確定後の自動再ゼロはない。

MEKF軸、ジャイロ校正、制御計算、固定3 ms補償、パルス上限、ESTOP、足角度の係数は変更しない。
0.47.2で修正したカメラタスクの8192バイトスタックと、既存のUSB診断を維持する。

## 同じフレームの画像と診断を保存する

装置WebUIの「検出画像を確認」から、測定停止中に1枚ずつ取得できる。
160×120のグレースケール画像へ、元の320×240座標で得た選択位置と走査帯を重ねる。
緑は検出候補、黄色は未確定・別候補。枠は観測帯であり、白四角の輪郭を推定した矩形ではない。
`scan_y`は選ばれた走査行の中心であり、マーカー全体のY重心ではない。

画像と、その画像の角度・ゼロ・候補・選択理由・時刻・sequenceを一つのJSONへ保存する。
`pixels_gray8_base64`は行優先の160×120=19,200バイトをBase64化したもの。
この値を復号すれば、後から同じ画像を再解析できる。通常の診断JSONは別途保存可能。

カメラ側の19,200バイトとHTTP側の19,200バイトはPSRAMに置く。
カメラ側では短いmutex区間で画像と観測情報を同時に更新し、HTTP側がその組を固定コピーする。
コピーに割り込み禁止のspinlockを使わず、ネットワーク送信中にmutexを保持しない。
mutexが使用中なら、その回のプレビュー更新・取得を失敗として扱う。追跡処理は待機しない。

`POST /vision/capture`が画像を固定し、tokenとCRC付きmanifestを返す。
`GET /vision/chunk?token=...&offset=...&length=...`で最大4096バイトずつ取得する。
各チャンクは既存のFCH1ヘッダーを用い、ブラウザはチャンクと画像全体のCRCを確認する。
次の撮影要求はtokenを変更するため、途中で他の撮影が入っても混ざった画像を成功として保存しない。
画像転送は測定中・コマンド待機中・ログ構築中には受け付けない。
UIも取得中は測定開始等を無効にするが、緊急停止は引き続き操作可能。
自動画像配信や常時ストリーミングは行わない。

## 確認方法と限界

1. 新しい版を書き込み、再起動後に胴体と両足を直立させ、2秒以上静止してゼロ点を取得する。
2. 測定開始は押さず、「検出画像を取得」→「画像付き診断を保存」で直立時を保存する。
3. 両足を地面に固定して胴体だけを前後に傾け、同じ操作で2枚目を保存する。
4. 両画像の選択位置が同じ左右の白四角に重なるか、ゼロ位置と現在位置の差が左右で妥当か確認する。
   ゼロ点待ち・未検出になる場合も画像を保存できる。既存の診断JSONには処理時間・FPS・失敗数も残る。
5. 傾斜が速すぎる場合は位置急変として一時的に無効になる。静止後、再捕捉を待って取得する。

ホスト試験の失敗再現画像は、修正後に右22.9857°・左22.7703°となる。
これは同じ既存係数を使って候補の選び方を修正した結果であり、実機精度の保証ではない。
全Y探索、左右帯の分離、競合候補、別明部の混合防止、追跡飛び、再捕捉、欠落画像、
誤ったゼロ候補、ゼロ取得中の変動を試験する。
画像の固定コピー、転送中の別フレームとの分離、全体CRC・token不一致の拒否も試験する。
最大イベント数と足768フレームを含むRWLOGの完全性、CSVの追加項目と旧ファイル互換も確認する。
既存の取得・制御・MEKF・カメラタスク・ブラウザ再接続の検証は`bash tools/test_runtime.sh`で実行する。

検出は白さと位置のヒューリスティックであり、任意の背景に対する物体識別ではない。
近くに紛らわしい明部がある場合、移動後の再捕捉で別物を選ぶ場合、取り付けが変わって中立位置が
±35 pxの範囲を外れる場合は、画像を見て条件や校正を見直す必要がある。
全17位置の探索による処理負荷と、追加のプレビューコピーの実機負荷は診断値で確認する。
APIが返す画像はその時点の最新保存フレームであり、取得要求後に新しい露光を強制するものではない。
表示する経過時間で新しさを確認する。測定終了・ESTOP後はカメラが停止し、最終保存画像となる。
160×120への縮小は診断用であり、元の全画素画像は保存しない。
検出重心の計算範囲を変えているため、旧校正との小さなオフセット差も実画像で検証が必要。
Xが約35 pxの姿勢は旧校正範囲外であり、今回の検出修正で範囲外の角度精度まで確定したわけではない。
必要なら、同じ物理マーカーを追っていることを確認した後で角度校正を更新する。

取り付け方向と座標の根拠は[座標監査](ROBOT_COORDINATE_AUDIT_20260924_JA.md)に記録する。
