# 0.47.23: Wi-Fiを維持し、運転中のHTTPを休止

0.47.22ではWi-Fi停止によってPC側でSSIDへの接続し直しが必要になる場合があった。
0.47.23はAPを継続し、開始前にHTTPの接続と待ち受けだけを閉じる。
本体は開始同期5秒・測定30秒・終了同期5秒を実行し、ログ確定後にHTTPを再開する。
Wi-Fiのバックグラウンド処理が残るため、処理時間は実機で再比較する。

## 実行順序と復帰

1. 明示的STARTに202を返す。ブラウザは送信前から自動GETを休止する。
2. 応答送信後350 ms待ち、現在のHTTPクライアントとポート80の待ち受けを閉じる。
   待ち受け停止を確認できた場合だけ制御タスクにSTARTを渡す。
3. 開始同期から終了同期まで、`handleClient()`、状態JSON生成、プレビュー要求処理を休止する。
   低優先度のHTTP担当は20 msごとに開始結果・終了状態のみを確認する。
4. 制御タスクは通常終了・ESTOPとも、`sealCompletedLog()` と `feet.finishRun()` の後に
   非稼働状態を公開する。HTTP担当はその公開を待つ。
5. ポート80を再び開く。失敗した場合は1秒間隔で再試行する。
   開始拒否・開始タイムアウト・開始直後のESTOPにも同じ復帰経路を使う。
   5秒の開始タイムアウトではSTOPを要求し、開始要求の決着と非稼働を待ってから復帰する。

AP停止イベントを待つ段階と `esp_wifi_stop/start` を削除した。
運転開始・終了・HTTP復帰の再試行では、Wi-Fiモード、SSID、IP、DHCPを再設定しない。
運転終了をPC側のタイマーで決めない。45秒を超えて運転中でも本体HTTPは休止を続ける。

使用ライブラリは `espressif32@6.7.0` / Arduino ESP32 2.0.16。
上流の [WebServer.cpp](https://github.com/espressif/arduino-esp32/blob/2.0.16/libraries/WebServer/src/WebServer.cpp)
と [WiFiServer.cpp](https://github.com/espressif/arduino-esp32/blob/2.0.16/libraries/WiFi/src/WiFiServer.cpp)
で、HTTPの `stop()/begin()` がルート登録を維持してソケットを閉じ直す動作を確認した。
WebServerの停止とは別に、現在のクライアントも明示的に閉じる。

## データと制御の関係

- HTTP復帰で `WebUi::begin()`、IMU初期化、ロガー初期化・消去、足ゼロ点初期化、
  `ImmutableExport::reset()` を呼ばない。boot ID・観測バッファ・転送tokenを維持する。
- ログを保持するPSRAM、足観測、MEKF、モーターI/OはHTTP担当から独立して動く。
  RWLOGのサンプル・イベント・足フレーム、4 KBチャンク、CRC、再取得キャッシュは継続する。
- 完了後は明示的な次回STARTまでHTTPを維持する。ダウンロード待ちや通信中断でログを消さない。
- USB診断は起動ごとにOFF。ONでも運転中のヒープ・スタック走査は延期する。
- 前後±90度の姿勢STOP、横倒しを対象外とする判定、ESTOP保持は0.47.22と同じ。
- 目標8度、30秒、3 ms補償、300 mA・最大100 msパルス、制御計算、MEKF、足校正係数、
  校正範囲、計測予算2,500 µsとその計測端点は変更しない。

## ブラウザの動作

Wi-Fi接続と画面を保ったまま待つ。画面はPC側の時計でWeb復帰までの目安を表示する。
通常は約45秒後に状態GETを自動再開する。途中STOP後は「終了・Web復帰を確認」で
早めに状態GETを試せる。画面の時間は実際の運転進行を確認した値ではない。
運転中の新規ページ取得とWeb STOPは提供しない。

開始応答が失われてもSTARTを自動再送しない。開始前から通信中だった状態GETが
後からREADYを返しても休止を解除しないよう、要求時点の世代を確認する。
これにより、古い応答をきっかけとした運転中の定期GET再開を防ぐ。
既存の `offline_run` 応答キーとsessionStorageキーは互換性のため維持する。

AP維持でも、電波環境やPCの接続方針に依存する切断は実機確認が必要。
本体の無線タスク、ビーコン、Wi-Fi/IPスタックの処理は残る。

前回の正常完走1本と追加4本。全て目標8度・30秒・固定3 ms、FINISHED。
意図的な転倒STOPの `315957546` はこの5本に含めない。

IMU内部の取得から物理モーター出力までを保証する指標ではない。
ホストのIMU取得間隔は別の指標で、この5本の最大は3,358 µs。

全5本のCRCが正常。添付足CSV全2,000行はRWLOGからの復号値と一致。
IMUキュー落ち・取得連番欠落・ドライバ読み取り失敗・足フレーム連番欠落は0。

全5本の通常ログでMEKF採用と姿勢値の有限性を確認した。

## 検証と次の実機測定

ホスト回帰試験ではHTTP停止完了前のSTART禁止、無線APIなしの開始経路、
開始拒否・タイムアウト・即時STOP、HTTP再開失敗の再試行、連続2回の完走、
時計周回を確認する。ブラウザ試験では古いGET応答、START応答消失、休止中の自動GET抑止、
FINISHED/ESTOP後の取得可能状態、保存済みカウントダウンを確認する。
既存の実C++シリアライザーとブラウザ転送試験で通信中断後の続行・全体CRC・足CSVを確認する。
これらは実無線の接続維持や2.5 ms予算達成を代替する試験ではない。

`bash tools/test_runtime.sh` は全件通過。1,480,263 bytesのRWLOGを8,192 bytesで
中断して再開し、全バイト・CRC一致と768行の足CSV生成を確認した。
姿勢STOP、MEKF、制御計算、IMU取得の既存回帰試験も通過した。

0.47.23はまず1回、目標8度・30秒・USB診断OFFで測定し、Wi-Fi接続維持、Web復帰、
RWLOGと足CSVの保存を確認する。処理時間とログ整合性を確認してから残り4回を取る。
比較する基準は、同じ計測端点で超過0回、最大時間、取得欠落、足観測とログ保存の継続。
実機比較前に0.47.23で超過ゼロを達成したとは判定しない。
